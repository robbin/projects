05近期项目（AI / Agent）

围绕 Agent 的工程实践：让 Agent 能接力干活、能看新闻、能操作手机，也能从旧应用里把数据取出来。

grokbot-local-agent

精选

让 Grok Bot 把重活交给同机的 Pi Agent，任务干完后反过来把 Bot 叫醒；
还能在 Telegram 上全程旁观 Pi 怎么干活。

  • 每个委派任务都有 ID、状态和产物目录，完成后只通过 webhook 发送 id、owner、state 和 exit_code，Bot 醒来后回读文件、核对结果再汇报。
  • 对话轮次可能早已结束，通知只是延迟优化，磁盘状态才是唯一事实来源；漏掉 webhook 时用 pi-task pending 补收，而不是重跑任务。
  • 给任务记录派发者 owner，pending 和 ack 都按 owner 过滤，避免多个 Bot 互相汇报别人的工作。
  • 可选的 Telegram 旁观模块：每个 Pi 会话在手机上一条滚动更新的进度消息，回复结束另发最终结果全文；只发不收，推送前自动遮蔽疑似密钥。
  • Node.js 22+
  • Pi RPC
  • Bash
  • Webhook
  • Telegram Bot API

agent-relay

精选

用 Git 仓库做传输层，让本地 Agent 和云端 Agent 双向自动接力任务。

  • 一个任务一个 Markdown 文件，状态从 pending 到 accepted 再到 done 或 blocked，结果写回同一个文件；Git 负责传输和历史，不需要数据库。
  • 双向自动派发：本地交给云端的任务由 webhook 唤醒云端 Bot；云端交给本地的任务写上 Executor 字段，由本地 relay-runner 每 5 分钟自动领取，派给 Paseo 等 Agent 执行，做完写回结果。
  • 安全边界写进实现：按任务显式 opt-in、单任务锁、干净工作区检查、目录白名单，角色或模型不可用就标 blocked 不偷换，发布删除部署这类操作只准备不执行。
  • 附带任务协议、只拉取的同步脚本、可选的自动执行器、GitHub Actions 通知模板和本地／云端两份 Agent skill，是一套照着部署的参考实现。
  • 三层安全防护：目标目录按真实路径做白名单校验（拒绝 .. 和软链接逃逸）；任务正文命中密钥、私钥、上传命令等敏感模式即拦截，不启动执行者；执行者只提交不推送，结果出口扫描疑似密钥，干净才由 runner 推送，命中就暂停。

x-news

社区热点新闻站 news.fankai.me 的源码：报告用 Markdown 写，导航和首页在构建时生成。

  • Daily、中文话题和英文话题三类报告按目录增删即可，hooks/autonav.py 在构建时生成导航、分类 index 和首页，不用手改 mkdocs.yml。
  • 中英文用 mkdocs-static-i18n 的后缀布局，根路径是中文、/en/ 是英文，缺英文稿自动回退；页头、首页和页脚订阅入口由 presentation.py 注入。
  • push 到 main 由 GitHub Actions 构建发布到 GitHub Pages，报告本身由 News bot 通过 x-research 技能生成，仓库里不放凭据和订阅者数据。
  • MkDocs Material

android-adb-control

给 Agent 的安卓手机操作技能：先看界面，再走一步，验证结果后才决定下一步。

  • 纯指令型 Agent Skill，不是 MCP Server 或后台服务；Pi、Codex CLI、Claude Code 和 OpenCode 共用同一份 SKILL.md 与参考文档。
  • 默认限制 30 次设备状态变更和 5 分钟，发送、购买、删除、安装等动作必须单独授权，发送状态不明时不会自动重发。
  • 明确不碰锁屏、验证码、支付验证和企业策略，也不做无人值守监控；截图和 UI XML 可能带隐私，交云端模型前要先确认数据策略。

wechat-exporter

把 macOS 微信 4.x 的 SQLCipher 本地库恢复成标准 SQLite，用来导出自己的聊天记录和联系人。

  • 原来依赖的上游项目已下线，仓库改成一套可执行的实现规范：页面布局、密钥派生与 HMAC、逐页解密、WAL 处理和验收标准，Agent 可以据此从零写工具。
  • 验收要求全页 HMAC、独立内容比对和逐库结论，只看文件头、表名或 integrity_check 不算恢复成功；未覆盖的版本差异必须明说。
  • 产物是明文 SQLite，不是整理好的聊天文本，正文编码、联系人与附件关联仍需后续处理；也只覆盖客户端 db_storage 中实际存在的记录。

sinatratest

用 Sinatra 写 Ruby Web Service 的服务端模板项目，把 Ruby 的性能尽量榨出来。

  • 轻量组合：Sinatra + ActiveRecord + MySQL，配 Oj 做 JSON 序列化，用 second_level_cache 和 Dalli 做对象缓存，生产环境跑在 Rainbows 上。
  • test.md 用 siege 压测，对比了 Fiber 池、多线程、多进程三种并发模型，以及 Rainbows 和 Puma、Dalli 和 redis-store。
  • 实测结论：同样 2 个进程，Fiber 池或多线程完成同一批请求约 72–77 秒，多进程要约 251 秒，快了 3 倍多，每个进程内存只有 50–60MB。
